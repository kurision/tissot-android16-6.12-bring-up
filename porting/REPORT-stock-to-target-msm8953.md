## 2. Test strategy (revised per user: combined USB+ashmem+PLL, reset gates removed)

The user superseded the USB-only plan: the next diagnostic boot tests **USB + ashmem + PLL together**, with **reset-test service gates removed** (current `scripts/initramfs-diag/init.c` has `BOOT_DEADLINE_SECONDS` default `0` at `:67-69` — watchdog off by default since snapshot60 run31 — and no `HEADLESS`/`HALGATE`/`DISPLAY_GATE` service stubs; the five original service RCs are preserved in host smoke per the tracker contract).

Per-subsystem verdicts are preserved, but isolation is weaker by design:

| Subsystem | Pass signal on the combined boot | Confound if failed |
|---|---|---|
| USB UDC | `uname -r` 6.12 kernel; `vendor.usb.controller=sys.usb.controller=7000000.usb`; `/config/usb_gadget/g1/UDC=7000000.usb`; `/sys/class/udc/7000000.usb/state` present; no `7000000.dwc3` repeat (configfs requires a name from `/sys/class/udc/` — `https://www.kernel.org/doc/html/v5.7/usb/gadget_configfs.html#enabling-the-gadget`; run124 prep in `porting/TRACKER-kgsl-port.md`) | adbd running alone is not success |
| ashmem | `/dev/ashmem` exists; zero `Failed to create ashmem` / `Unable to stat ashmem device` in early-logcat; `SystemServer` passes `ApplicationSharedMemory.create` | Without USB transport this is logdump-only evidence |

### B4 — KGSL/Adreno506: partial runtime/probe, NOT built-only; CP/EGL/render unresolved

The vendored `drivers/gpu/msm/` driver has executed on-device. Per `porting/TRACKER-kgsl-port.md` Stage-3 log (runs `snapshot60/run2..run36`): **run27 binds** (`interrupt-names = "kgsl_3d0_irq"` fix — no `probe with driver failed`; `/dev/kgsl-3d0` opened by userspace, `kgsl_open` traces, probe at ~14.4 s); run29 full boot (3.07 MB / 26,605 lines to ~932 s, clean `DIAG: EOF`, probe at ~4.56 s); **run35 PASS** (300 s+ Android, `GPU BW scaling failure` 0, regulator/`supply vdd` errors 0, probe failures 0); run37/38/39 continue the probe-succeeds line (four driver bugs fixed by absence incl. `qcom,highest-bank-bit`, msm-bus index, legacy-regulator guards). Classify as **partial runtime/probe**: node built, GPU binds, `/dev/kgsl-3d0` opens from userspace. **Unresolved:** command-processor / EGL / render — the vendor EGL blob (`libGLESv2_adreno.so`), SDM HWC, and gralloc have no proven render on this tree; the snapshot58 `surfaceflinger: no suitable EGLConfig found` abort remains the last known rendering blocker, not re-proven fixed.

The run123 `gpu_ahb_clk` line must not be called a fatal GPU-probe failure without the helper path. Code read (this session):

- `drivers/gpu/msm/kgsl_iommu.c:2732-2740` (`_kgsl_iommu_probe` clock loop): `devm_clk_get(iommu_dev, cname)` failure logs `dt: Couldn't get clock: %s` and **returns `-ENODEV`**; `kgsl_iommu.c:2764-2812` continues through `qcom,smmu-kgsl-cb` children and `kgsl_dt_devices[] = { "qcom,kgsl-smmu-v2" → _kgsl_iommu_probe }` (`kgsl_iommu_probe` returns `-ENODEV` if no node). The `gpu_ahb_clk` miss (`run123-logdump.log:532`) is on this **KGSL-IOMMU clock-names path**, which resolves against the GPU device with no platform device of its own.
- Stage-3 finding 13 (tracker) is authoritative for behavior: the clock-names legitimately do not resolve; `_kgsl_iommu_probe` returning `-ENODEV` there is **non-fatal as a separate platform driver — the GPU still binds and `/dev/kgsl-3d0` opens**; making that probe succeed instead (run34/run36 renames) killed the phone ~60 s in before diag init wrote anything, twice. The run123 warning is therefore a real DT/clock-binding defect on the IOMMU path, not proof the GPU bind failed. Next is DT/clock-provider alignment plus Stage-3-style `kgsl_open`/pwrlevel/firmware evidence, then EGL/SF — not a "first probe" claim.

Remaining KGSL churn stays scoped per tracker: sync→`dma_fence` (3 sites), `msm_bus`→icc (`drivers/gpu/msm/msm-bus-compat.c:1-63` interconnect-backed stand-in reading legacy `qcom,msm-bus,*` DT and voting on `gpu_icc_path`, absent path = no-op; native `drivers/interconnect/qcom/msm8953.c` has no gpu master), IOMMU shims, zap SCM (`pas_init_image`/`pas_auth_and_reset`), `a506_zap.mdt` flat-name staging.

## 3. Latest reset evidence (run118–120 supersedes older theories)

Do not present run97 PON/early-timing hypotheses as current. The latest narrowed mechanism in `porting/TRACKER-kgsl-port.md`:

- **Run118: SEA caught; silent reset = Linux panic path.** `g99553226bb68-dirty`, `panic=0`: `hw_init`/`overlay_start` exonerated (gdsc on, clocks on, 5/5 writes, `ctl_start`/`pp_resume`/`splash_cleanup` rc=0), then `SEA ESR=0x96000010 FAR=... PC=...b42e88` in `kworker` — bus fault **after** successful overlay_start. `panic=0` hung (user force-rebooted); snapshots predate the SEA by ~400 ms so USB is the sole final-window record.
- **Run119: SEA is the MDSS IOMMU fault handler reading an unclocked `CB_FSR`.** `gf7d99b6067a0`, `panic=0`, same late path (`mdss_fb_open by mm-pp-dpps` → hw_init → ctl/pp/splash rc=0), tail (`run119-usb.log`, ~159.68 s): `SEA: ESR=96000010 FAR=...840f7058 PC=...80b42e88`, `SEA2: pc=readl_relaxed+0x38 (IRQ stack)`, `SEA3: area=+0x2000 phys=0x01e35000 VM_IOREMAP caller=ioremap_prot`. Decode: `0x01e35000` = `apps_iommu iommu@1e20000` + `iommu-ctx@15000` (the context bank both MDSS SMMU children use, `iommus = <&apps_iommu 0x15>` per tissot-mdss DT); offset `0x58` = `ARM_SMMU_CB_FSR` (`drivers/iommu/arm/arm-smmu/arm-smmu.h:198`). Chain: MDP fetch faults in its SMMU context → context-fault IRQ → `qcom_iommu_fault()` reads `CB_FSR` → external abort → oops → panic. Same PC as run118 (the earlier `drm_dp_pcon_frl_configure_2` symbol came from a later build's `System.map`; in-kernel `%pS` is authoritative; runs 89/93 IRQ-stack `readl_relaxed+0x38` fit).
- **Mechanism (code-read):** `qcom_iommu` holds runtime-PM refs only around attach/map/unmap; the fault handler read registers with no reference. Upstream fixed the same class in `arm-smmu` with `pm_runtime_get_if_active()`. Current tree already contains that guard: `drivers/iommu/arm/arm-smmu/qcom_iommu.c:189-230` — `qcom_iommu_fault` does `pm_runtime_get_if_active(iommu_dev) <= 0` → logs `context fault IRQ while IOMMU suspended, cb=%d` and returns `IRQ_NONE` instead of the unclocked `iommu_readl(ctx, ARM_SMMU_CB_FSR)` (`:210`), then the `FAULT`-bit check (`:212`), `FSYNR/FAR` reads, `report_iommu_fault`, FSR write + `RESUME_TERMINATE`, `put`. Run120 adds this guard (proves-or-kills the hypothesis; a level IRQ may storm until the core disables it) plus read-only `DIAG cpuclk` (APCS PLL/mux reads from stock offsets; the port still has no CPU clock/cpufreq/CPR driver).
- **Still open:** why the MDP faults at all (expect `Unhandled context fault: fsr= iova=` once the handler can read while active). DSI-PLL imbalance stays a separate display defect, not the resetter.
